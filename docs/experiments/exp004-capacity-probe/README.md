# exp004 · 容量探针：LoRA r16 → r64（Issue #3）

日期：2026-09-25 训练 / 2026-09-26 判读。方案：[docs/plan/004_weakness-probe.md](../../plan/004_weakness-probe.md)。
**结论一句话**：把 rank 从 16 提到 64（α 同步 32→128）→ **全面崩坏**（−23.31pp，每个 source 都退化）。这不是「容量受限」，是**优化失败**。⚠️ **非单变量对照**——训练切分（34,146 vs 35,948）与评测集（1,802 vs 1,892）同时变了，故**不能**把失败单独归因于 rank（2026-09-28 更正，详见「设计」与判读第 1 条）。

## 问题与判据（预注册，训前锁定）

**问**：exp003 细粒度诊断定位的弱项（`routing_v2` 的 `complete_*` 60.5–66.7%、`policy_v2` 的 `decisive_missing` 67% 等），是**训练不充分**还是 **2B 容量上限**？

**设计**：LoRA rank `16 → 64`（`alpha` 同步 `32 → 128`），超参其余部分与 exp002 相同；**但训练切分与评测集也不同**（训练 34,146 vs 35,948；评测 holdout2 1,802 vs holdout1 1,892）——**不是单变量对照**（2026-09-28 更正）。

**判读表（训前锁定）**：

| 预注册结果 | 结论 | 下一步 |
|---|---|---|
| 新封存集总体 **≥ +3pp** 且弱项同步提升，强项不退化 | 容量受限 | 继续加容量 / 考虑更大底座 |
| 变化 **< +1pp**（噪声内） | 非容量问题 | 转向训练充分度（2 epoch 探针） |
| 强项退化 **>2pp** | 容量换能力失败 | 回退，重新设计 |

⚠️ **判读表未覆盖「训练失败」这一分支**——而这个分支恰恰发生了。这是本轮的第一个方法论教训。

## 判读

### 为什么这是「训练失败」而不是「容量不够」

三条独立证据：

1. **`train_loss` = 0.880**，而 exp002 的 r16 是 **0.457**。容量更大者 loss **更高**，即**连训练集都没拟合上** → **没优化好**。⚠️ 本仓各轮**都没有划出验证集**（只有 `train_loss`），故此处**不足以**下「不是过拟合」的定论——能排除的只是「训练集拟合更好却更差」这一种情形（2026-09-28 更正）。
2. **双口径有效率均 100%**（1,802 条全部输出合法单字母）→ 输出协议完好，**不是解析或格式问题**，是模型真的没学会。
3. **每个 source 都退化**，连最饱和的 `boolq`（73.2%→50.7%）也不例外。**没有一处是「容量换来了局部收益」**。

### 跨集对照（须谨慎：两集不同）

| 集 | base | 微调 | Δ |
|---|---:|---:|---:|
| 原 holdout（1,892，exp002 的 r16） | 51.11% | **80.50%** | **+29.39pp** |
| holdout2（1,802，本轮 r64） | 51.22% | **27.91%** | **−23.31pp** |

**base 在两集上差 0.11pp**（51.22% vs 51.11%）→ 两集难度相当。故「r16 大幅**高于**其 base」与「r64 大幅**低于**其 base」**方向相反**——足以支持「r64 训练失败」，**不需要**跨集直接相减。

### 对照预注册判读表

| 预注册分支 | 是否命中 |
|---|---|
| ≥+3pp 且弱项同步提升 → 容量受限 | ❌ |
| <+1pp → 非容量问题 | ❌（变化远超 1pp，且为负） |
| **>2pp 强项退化 → 容量换能力失败** | ✅ **命中** |

### ⚠️ 不能推出的结论

- **不能**说「容量不是瓶颈」——r64 崩了，**我们没拿到 r64 的真实能力**。判读表假设「更大 rank 至少能跑通」，该假设不成立。要问「容量是否受限」，得先让 r64 跑通。
- **不能**拿本次结果声称「2B 已到上限」。

### 最可疑根因

`α/r` 比值两臂相同（都是 2），但 **r64 参数量是 r16 的 4 倍，而 lr 2e-4 未随 rank 缩放** → 相同 lr 下有效更新幅度过大，可能发散或落到坏解。**这是假设，非结论**——验证需单变量改 lr（已立 #15（内部追踪项））。

## 结果的时间边界与规模边界

- **时间边界**：2026-09-25 的运行，依赖当时的代码 commit、Modal L4 环境与镜像版本。
- **规模边界**：单次 2B 底座、单数据集（34,146 条）、单 seed、单 L4。**不构成「LoRA 配方在 2B 上的普遍规律」**——只记录「本仓这套配方在这一个 rank 上崩了」。
- **适用边界**：`research_taxonomy_v21` 的崩塌（100%→8.2%）是本轮最强信号，但它来自**跨集比较**（100% 在原 holdout，8.2% 在 holdout2），该源在两集的题不同。

## 结论与下一步

**结论**：容量探针**未能回答原问题**——它变成了一个「配方失败」的记录。可确证的是：**在本底座上，rank 16 → 64 的这次尝试把成绩从 80.50% 打到 27.91%**。⚠️ **不能**据此说「配方对 rank 极敏感」——训练切分（34,146 vs 35,948）与评测集（1,802 vs 1,892）也不同，**不是「只换 rank」**，rank 的效应未与它们分离（2026-09-28 更正）。

**下一步**：见 #15（内部追踪项）（r64 崩坏的根因定位，最小可判读集 = 单变量改 lr，≈$5）。**在它出结论前，不应基于本次结果对「容量是否受限」下任何判断。**
